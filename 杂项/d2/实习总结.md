### 🔥 1. SSE流式响应 - AI对话模块（顶级亮点）

基于uni.request的`enableChunked`模式，封装了SSE（Server-Sent Events）流式响应工具类，用于AI升学规划对话功能。

**技术难点与解决方案**：

| 难点 | 解决方案 |
|------|---------|
| 小程序不支持EventSource API | 手动解析text/event-stream协议 |
| 分块传输数据可能被切断 | 使用sseBuffer缓冲区累积数据 |
| 小程序不支持TextDecoder | 手写UTF-8字节流解码器 |
| 请求超时无响应 | 120秒超时控制 + 请求取消机制 |

**核心代码逻辑**：

```javascript
// 1. SSE缓冲区累积处理
this.sseBuffer += responseText
const lines = this.sseBuffer.split('\n')
for (let i = 0; i < lines.length; i++) {
    const line = lines[i].trim()
    if (line === '') {
        // 空行表示一个完整事件，处理并清空
        this.handleSSEEvent(eventData.event, eventData.data)
    } else if (line.startsWith('event:')) {
        eventData.event = line.substring(6).trim()
    } else if (line.startsWith('data:')) {
        eventData.data += line.substring(5).trim()
    }
}

// 2. 手写UTF-8解码器（兼容小程序环境）
if (charCode < 0x80) {
    text += String.fromCharCode(charCode) // 单字节
} else if (charCode < 0xE0) {
    charCode = ((charCode & 0x1F) << 6) | (bytes[i+1] & 0x3F) // 双字节
}
```

**面试话术**：
> 由于小程序环境不支持浏览器的EventSource API，我们基于uni.request封装了SSE工具类。核心难点有两个：一是分块传输时数据可能在任意位置被切断，我用缓冲区累积数据，遇到空行才表示一个完整事件；二是小程序环境不支持TextDecoder，我手写了UTF-8解码器处理ArrayBuffer。

### 🔥 3. 路由守卫 - 全局登录拦截

通过重写uni导航方法，实现跳转前的权限校验，拦截未登录用户访问受保护页面。

**设计思路**：

```
1. 重写 uni.navigateTo/redirectTo/reLaunch/switchTab
2. 跳转前检查：token存在 → 放行
3. token不存在 → 检查白名单 → 在白名单则放行
4. 不在白名单 → 弹窗提示登录，携带returnUrl
5. 页面onShow兜底检查（防止URL直接访问）
```

**核心代码逻辑**：

```javascript
// 重写导航方法实现前置拦截
const originalNavigateTo = uni.navigateTo
uni.navigateTo = function(options) {
    if (shouldInterceptNavigation(options.url)) {
        handleAuthRequired(options.url)
        return Promise.reject({ message: '需要登录', code: 401 })
    }
    return originalNavigateTo.call(this, options)
}

// 校验逻辑：token优先 → 白名单兜底
function shouldInterceptNavigation(url) {
    const token = uni.getStorageSync('token')
    if (token) return false  // 有token不拦截
    
    const isInWhiteList = config.routeWhiteList.some(path => 
        url.split('?')[0].startsWith(path)
    )
    return !isInWhiteList  // 不在白名单则拦截
}
```

**面试话术**：
> 我们实现了全局路由守卫，核心思路是重写uni的导航方法，在跳转前进行权限校验。检查逻辑是：先看有没有token，有就放行；没有就检查白名单，白名单内的页面不需要登录也能访问。同时在页面onShow中做兜底检查，防止用户通过URL直接访问受保护页面。

### 📌 技术点1：视频防作弊机制

**简历原文**：
> 设计maxWatchTime状态机，在timeupdate事件中做增量校验，拦截未观看区域的快进操作

#### 🗂️ 代码位置
```
pages/course/task/detail.vue  （第240-290行左右）
```

#### 🔧 实现原理

**核心状态变量**：
```javascript
data() {
    return {
        maxWatchTime: 0,    // 用户看过的最远位置（秒）
        lastPlayTime: 0,    // 上一次合法的播放时间
        isCompleted: false  // 是否已完成（完成后可任意拖拽）
    }
}
```

**核心逻辑**（在 `onVideoTimeUpdate` 事件中）：
```javascript
onVideoTimeUpdate(e) {
    const currentTime = e.detail.currentTime
    const timeDiff = currentTime - this.lastPlayTime
    
    // 正常播放（误差3秒内）：更新位置
    if (Math.abs(timeDiff) < 3) {
        this.lastPlayTime = currentTime
        this.maxWatchTime = Math.max(this.maxWatchTime, currentTime)
    } else if (timeDiff > 0) {
        // 向前快进：检查是否超过已观看部分
        if (!this.isCompleted && currentTime - this.maxWatchTime > 1) {
            // 拒绝跳转，强制回退
            this.videoContext.seek(this.lastPlayTime)
            uni.showToast({ title: '未观看部分禁止快进', icon: 'none' })
        }
    }
    // 向后回退：允许
}
```

**设计思考**：
- `maxWatchTime` 只增不减，记录历史最远位置
- 3秒容差是考虑视频分片加载可能有跳跃
- 已完成的视频允许任意拖拽复习

#### 💬 面试话术
> 我设计了一套视频防作弊方案，核心是维护一个 maxWatchTime 状态机，记录用户看过的最远位置。在 video 组件的 timeupdate 事件中，我检测当前播放位置和上次位置的差值：如果差值小于3秒，说明是正常播放，更新 maxWatchTime；如果差值过大且超过了 maxWatchTime，说明用户在快进未看过的部分，就调用 seek 方法强制回退，并给出提示。同时考虑了全屏切换时的边界情况，用一个标志位暂停检测。

### 📌 技术点2：SSE流式响应封装

**简历原文**：
> 基于enableChunked实现AI对话的流式输出，手动解析text/event-stream协议，使用缓冲区累积处理分块数据

#### 🗂️ 代码位置
```
common/sseUtil.js           # SSE工具类封装
pages/ai/planning.vue       # AI对话页面（实际使用）
```

#### 🔧 实现原理

**为什么需要手动封装**：
- 浏览器有原生 `EventSource` API，但小程序没有
- 需要基于 `uni.request` + `enableChunked: true` 自己实现

**核心流程**：
```
1. 发起请求，开启分块传输
2. 监听 onChunkReceived，接收 ArrayBuffer 数据块
3. 将 ArrayBuffer 转为文本（手写UTF-8解码器）
4. 累积到缓冲区，遇到空行解析为完整事件
5. 根据事件类型（message/end）处理数据
```

**核心代码**：
```javascript
// sseUtil.js - 发起SSE请求
export const createSSERequest = (options) => {
    const requestTask = uni.request({
        url: fullUrl,
        enableChunked: true,  // 关键：开启分块传输
        header: { 'Accept': 'text/event-stream' },
        // ...
    })
    
    // 重写onChunkReceived，添加UTF-8解码
    requestTask.onChunkReceived = (callback) => {
        originalOnChunkReceived.call(requestTask, (chunk) => {
            // ArrayBuffer → 文本（手写解码器）
            const text = decodeUTF8(chunk.data)
            callback({ data: text })
        })
    }
    return requestTask
}

// planning.vue - 解析SSE数据流
parseSSEData(responseText) {
    this.sseBuffer += responseText  // 累积到缓冲区
    const lines = this.sseBuffer.split('\n')
    
    for (const line of lines) {
        if (line === '') {
            // 空行 = 一个完整事件结束
            this.handleSSEEvent(eventData.event, eventData.data)
        } else if (line.startsWith('event:')) {
            eventData.event = line.substring(6).trim()
        } else if (line.startsWith('data:')) {
            eventData.data += line.substring(5).trim()
        }
    }
}
```

**为什么需要缓冲区**：
- 网络分块传输时，一条消息可能被切成两块发来
- 例如 `data: {"content":"你` 和 `好"}` 分两次到达
- 必须累积起来，遇到空行才算完整

**手写UTF-8解码器**：
```javascript
// 小程序不支持 TextDecoder，手动解码
if (charCode < 0x80) {
    text += String.fromCharCode(charCode)  // 单字节 ASCII
} else if (charCode < 0xE0) {
    // 双字节：110xxxxx 10xxxxxx
    charCode = ((charCode & 0x1F) << 6) | (bytes[i+1] & 0x3F)
    text += String.fromCharCode(charCode)
} else if (charCode < 0xF0) {
    // 三字节：中文字符
    charCode = ((charCode & 0x0F) << 12) | ((bytes[i+1] & 0x3F) << 6) | (bytes[i+2] & 0x3F)
    text += String.fromCharCode(charCode)
}
```

#### 💬 面试话术
> 我们AI对话功能需要实现流式输出的打字机效果，但小程序不支持浏览器的 EventSource API。我基于 uni.request 的 enableChunked 模式封装了 SSE 工具类。
> 
> 核心难点有三个：
> 1. **分块数据累积**：网络传输时数据可能在任意位置被切断，我用 sseBuffer 缓冲区累积数据，遇到空行才表示一个完整的 SSE 事件；
> 2. **协议解析**：手动解析 text/event-stream 格式，识别 event:/data:/id: 前缀；
> 3. **UTF-8解码**：小程序不支持 TextDecoder，我手写了 UTF-8 解码器，根据首字节的高位判断字符占几个字节，再按位运算拼接得到 Unicode 码点。

### 📌 技术点3：WebSocket长连接

**简历原文**：
> 实现消息推送模块，设计30秒心跳保活 + 5次自动重连机制，区分主动关闭与异常断开

#### 🗂️ 代码位置
```
util/websocket/messageWebsocket.js
```

#### 🔧 实现原理

**功能**：实时更新 TabBar 上的未读消息角标

**核心设计**：
```javascript
// 状态变量
let socket = null           // WebSocket实例
let heartbeatTimer          // 心跳定时器
let activeClose = false     // 是否主动关闭
let reconnectCount = 0      // 重连次数
const maxReconnect = 5      // 最大重连次数

// 心跳保活：每30秒发送ping
startHeartbeat() {
    heartbeatTimer = setInterval(() => {
        socket?.send({ data: 'ping' })
    }, 30000)
}

// 自动重连：异常断开时触发
handleReconnect() {
    if (reconnectCount < maxReconnect) {
        setTimeout(() => {
            this.connect()
            reconnectCount++
        }, 2000)  // 2秒后重连
    }
}

// 主动关闭：不触发重连
close() {
    activeClose = true  // 标记为主动关闭
    clearInterval(heartbeatTimer)
    socket.close({ code: 1000 })  // 1000=正常关闭
}

// 连接关闭事件处理
socket.onClose(() => {
    if (!activeClose) {
        this.handleReconnect()  // 只有异常断开才重连
    }
})
```

**为什么需要心跳**：
- NAT/防火墙会关闭长时间无数据的连接（通常60秒超时）
- 30秒发一次 ping，保证连接在超时前有活动

**为什么区分主动关闭**：
- 用户退出登录/切后台时主动关闭连接，不应该重连
- 网络波动导致的断开才需要自动重连

#### 💬 面试话术
> 我们用 WebSocket 实现了消息中心的实时推送，用来更新 TabBar 的未读角标。设计了三个关键机制：
> 
> 1. **心跳保活**：每30秒发送 ping 消息。因为 NAT 和防火墙通常有60秒的连接超时，30秒心跳可以保证连接不被中间设备关闭；
> 2. **自动重连**：连接异常断开时，最多重连5次，每次间隔2秒，避免瞬间大量重连请求冲击服务器；
> 3. **状态区分**：用 activeClose 标志区分主动关闭和异常断开。用户主动退出登录时设为 true，此时 onClose 事件中不触发重连。

#### 🔧 实现原理

**核心思路**：重写 uni 的导航方法，在跳转前检查权限

```javascript
// 保存原始方法
const originalNavigateTo = uni.navigateTo

// 重写导航方法
uni.navigateTo = function(options) {
    if (shouldInterceptNavigation(options.url)) {
        // 需要拦截：弹窗提示登录
        handleAuthRequired(options.url)
        return Promise.reject({ message: '需要登录', code: 401 })
    }
    // 不需要拦截：调用原始方法
    return originalNavigateTo.call(this, options)
}

// 同样重写 redirectTo、reLaunch、switchTab
```

**校验逻辑**：
```javascript
function shouldInterceptNavigation(url) {
    const path = url.split('?')[0]  // 去掉参数
    
    // 1. 有token → 放行
    const token = uni.getStorageSync('token')
    if (token) return false
    
    // 2. 没token → 检查白名单
    const isInWhiteList = config.routeWhiteList.some(
        whitePath => path.startsWith(whitePath)
    )
    
    return !isInWhiteList  // 不在白名单 → 拦截
}
```

**白名单配置**（config.js）：
```javascript
const routeWhiteList = [
    '/pages/tabbar/index',      // 首页
    '/pages/login/login',       // 登录页
    '/pages/article/detail',    // 文章详情（允许分享）
    '/pages/aigc/detail',       // AI作品分享
    // ...
]
```

**双保险设计**：
```javascript
// 1. 跳转前拦截（主要防线）
uni.navigateTo = function(options) { ... }

// 2. 页面onShow兜底（防止URL直接访问）

    this.checkCurrentPageAccess()
}
```

#### 💬 面试话术
> 我们实现了全局路由守卫，核心思路是重写 uni 的导航方法。在 navigateTo、redirectTo 等方法执行前，先检查用户权限：
> 
> 检查逻辑是：先看有没有 token，有就放行；没有就检查白名单，白名单内的页面（如首页、登录页、分享页）不需要登录也能访问。如果既没有 token 又不在白名单，就阻止导航并弹窗提示登录。
> 
> 同时在页面 onShow 中做兜底检查，防止用户通过扫码或浏览器直接访问受保护页面。这个双保险设计确保了无论哪种入口都能被拦截。

```javascript
uni.$uv.http.interceptors.response.use((response) => {
    const data = response.data
    
    // 成功
    if (data.code === 200) {
        return data.result
    }
    
    // 未登录
    if (data.code === 401) {
        showAuthModal({ content: '登录已过期' })
        uni.reLaunch({ url: '/pages/login/login' })
        return new Promise(() => {})  // 阻止后续操作
    }
    
    // 单设备登录冲突
    if (data.code === 4011) {
        uni.removeStorageSync('token')
        showAuthModal({ content: '账号在其他设备登录' })
        return new Promise(() => {})
    }
    
    // 业务错误：交给组件处理
    if (custom?.handleError === true) {
        return Promise.reject(data)
    }
    
    // 其他错误：统一toast
    uni.$uv.toast(data.message)
    return new Promise(() => {})
})
```

#### 🔧 OSS缓存策略实现

```javascript
// 缓存读取
const getCache = (cacheKey) => {
    const cacheData = uni.getStorageSync(CACHE_PREFIX + cacheKey)
    if (!cacheData) return null
    
    // 检查是否过期
    const elapsed = Date.now() - cacheData.timestamp
    if (elapsed < cacheData.expireTime) {
        return cacheData.data  // 未过期，返回缓存
    }
    
    // 已过期，删除缓存
    uni.removeStorageSync(CACHE_PREFIX + cacheKey)
    return null
}

// 带缓存的下载
export const downloadJsonFile = (url, cacheTime = 24*60*60*1000) => {
    // 1. 先查缓存
    const cached = getCache(getCacheKey(url))
    if (cached) return Promise.resolve(cached)
    
    // 2. 缓存不存在，发起请求
    return uni.request({ url }).then(res => {
        setCache(getCacheKey(url), res.data, cacheTime)
        return res.data
    })
}
```

#### 💬 面试话术
> 响应拦截器实现了统一的错误处理：200正常返回数据；401登录过期时弹窗提示并跳转登录页；4011是单设备登录冲突，需要清除本地token。对于某些业务错误，我设计了 handleError 配置项，允许组件自定义处理而非统一拦截。
> 
> OSS缓存策略是为了优化静态资源加载。我用本地Storage实现了一个带过期时间的缓存层，默认24小时过期。下载资源前先查缓存，命中就直接返回；未命中再发请求，请求成功后写入缓存。这样隐私政策、地区数据这类不常变化的内容就不需要每次都请求了。

## 七、面试常见问题准备

### Q1: 介绍一下你在实习中做的最有技术含量的功能？

> 有两个比较有技术含量的点。一个是视频防快进机制，通过维护maxWatchTime状态机，在timeupdate事件中做增量校验，拦截未观看区域的快进操作。另一个是SSE流式响应的封装，由于小程序不支持EventSource API，我手动解析text/event-stream协议，用缓冲区累积处理分块数据，实现了AI对话的打字机效果。

### Q2: 学习进度上报是怎么设计的？

> 采用"定时+事件"双触发机制。定时器每30秒上报一次心跳；同时在 onHide、onUnload 等生命周期和视频 ended 事件中强制上报。为了避免频繁请求，还加入了 lastReportTime 防抖机制。

### Q3: SSE和WebSocket有什么区别？你们为什么选SSE？

> SSE是单向的，服务器向客户端推送；WebSocket是双向的。AI对话场景是服务端流式返回内容，用户不需要在对话过程中持续发送数据，所以SSE更适合。而且SSE基于HTTP协议，不需要额外的握手过程，实现更简单。

### Q4: 小程序不支持TextDecoder，你是怎么解决的？

> 我手写了一个UTF-8解码器。UTF-8是变长编码，单字节字符高位是0，双字节高位是110，三字节是1110，四字节是11110。根据首字节判断字符占几个字节，然后按位运算拼接得到完整的Unicode码点。

### Q5: 路由守卫为什么要在跳转前拦截，而不是页面加载后检查？

> 用户体验更好。如果在页面加载后检查，用户会先看到页面内容再被弹窗打断，体验很差。跳转前拦截可以直接阻止导航，用户停留在原页面弹窗提示登录。但我们也在onShow中做了兜底检查，防止用户通过URL直接访问。

### Q6: WebSocket心跳机制为什么是30秒？

> 这是一个经验值的权衡。太短会增加服务器压力和客户端电量消耗，太长可能连接已经断开了还没发现。30秒是比较通用的选择，大部分NAT和防火墙的超时时间都在60秒以上，30秒心跳可以保证连接不被中间设备关闭。

### Q7: 遇到过什么印象深刻的bug？

> 真机调试时发现视频无法播放，但开发者工具正常。排查后发现是腾讯云OSS的防盗链策略导致的，协调后端同学配置了资源白名单后解决。这让我理解了OSS资源鉴权机制和跨端兼容性的重要性。

### Q8: 你在团队协作中扮演什么角色？

> 作为前端开发实习生，我独立负责录播课模块的开发。参与需求评审时会主动提出技术可行性建议；开发过程中与后端同学保持沟通，确保API接口设计合理；代码会走团队的 Code Review 流程，从中学习了很多最佳实践。
